## 1. Правила доставки файлов

### 1.1 Claude правит файлы сам, не диктует

Когда нужно внести правки в существующий код проекта — Claude применяет правки в своей рабочей копии и присылает готовый патч-архив. Не «вставь эту строку на строку 247» — это медленно, в этом всё равно есть ошибки, и пользователь не должен искать места вставки.

Исключение: если файл крошечный (1–10 строк изменения, не более 2 файлов) — можно дать просто текст с нужной строкой, но это исключение, а не норма.

### 1.2 Уникальные имена патчей

Каждый патч-архив имеет **уникальное имя**, не пересекающееся с предыдущими. Скачивание в `~/Downloads/` не должно создавать конфликта имён.

**Схема:** `bz5_recon_v<VERSION>_patch_<NNN>_<short_description>.zip`

Где:
- `<VERSION>` — целевая версия recon (например `0_4_0`)
- `<NNN>` — порядковый номер патча в рамках этой версии (`001`, `002`, ...). Не сбрасывается при смене темы внутри одной версии.
- `<short_description>` — 1-3 слова через подчёркивание, по сути изменений (`apk_rename`, `dev_options_fix`, и т. п.)

Примеры:
- `bz5_recon_v0_4_0.zip` — изначальный пакет v0.4.0 (новая версия = новое имя само по себе)
- `bz5_recon_v0_4_0_patch_001_initial.zip` — первый патч после initial
- `bz5_recon_v0_4_0_patch_002_apk_rename.zip` — второй патч
- `bz5_recon_v0_4_1.zip` — новая версия, нумерация патчей начинается заново с 001

Если Claude забыл номер и контекст сбросился — спросить пользователя или посмотреть в названиях уже скачанных файлов в его `~/Downloads/`.

### 1.3 Сохранение путей внутри патча

Архив-патч раскрывается в папку с тем же именем, что zip (без `.zip`), и внутри неё **зеркальная структура проекта**:

```
bz5_recon_v0_4_0_patch_002_apk_rename/
├── .github/workflows/build.yml
├── android/app/src/main/AndroidManifest.xml
├── lib/main.dart
└── pubspec.yaml
```

Это нужно, чтобы `cp -r .../patchdir/. /Users/alexandrbaiko/development/bz5_recon/` тривиально клал файлы в правильные места.

В архив попадают **только изменённые файлы**, не весь проект.

### 1.4 Полный пакет vs патч

- **Полный пакет** (`bz5_recon_v0_4_0.zip`) — при первом релизе версии, когда новых файлов много (несколько новых папок, новый функционал). Кладёт в проект все нужные новые файлы.
- **Патч** (`bz5_recon_v0_4_0_patch_NNN_*.zip`) — мелкие правки уже работающей версии. Только модифицированные файлы.

Пользователю всегда понятно из имени, что он получает.

## 2. Правила инструкций к сборке

### 2.1 Инструкции — это команды

Любая процедура (применение патча, сборка, git, отладка) — это **готовый блок команд bash**, который можно скопировать и выполнить целиком. Не прозаический рассказ, не нумерованный список «откройте файл, найдите, добавьте» — только команды.

Прозы между блоками должно быть минимум, и она объясняет **зачем**, а не **что**.

### 2.2 Стандартный блок процедуры

```bash
# 1. Распаковать патч (имя файла — конкретное, не плейсхолдер)
cd /Users/alexandrbaiko/development/bz5_recon
unzip -o ~/Downloads/<exact_patch_name>.zip -d /tmp/
cp -r /tmp/<patch_dir>/. .

# 2. Проверка
git status
# Ожидается:
#   modified: <список>
# Untracked:
#   <список, если есть>

# 3. Коммит и пуш
git add .
git commit -m "<conventional commit message>"
git push

# 4. Забрать APK (для CI-сборок)
# GitHub → repo → Actions → последний run → Artifacts → bz5-recon-<version>.<N>.zip
```

### 2.3 Ожидаемый `git status`

После любого патча Claude перечисляет, что именно должно появиться в `git status`. Это позволяет пользователю мгновенно увидеть, если что-то пошло не так (например `cp` упало или какой-то файл не дошёл).

### 2.4 Никаких placeholders в командах

Не `<path/to/project>`, не `~/Downloads/whatever.zip` — а конкретный путь `/Users/alexandrbaiko/development/bz5_recon` и конкретное имя патча.

## 3. Правила работы с CI

### 3.1 Sole source of truth — GitHub Actions

Локально Flutter не нужен. Сборка делается на push в `main` через `.github/workflows/build.yml`.

### 3.2 Артефакты сборки

- **Артефакт-обёртка:** `bz5-recon-<version>.<build_number>.zip`, где `<build_number>` = количество коммитов в `main`
- **APK внутри:** `bz5-recon-<version>.<build_number>.apk` (а **не** `app-release.apk`)
- Версия читается из `pubspec.yaml` поля `version:`
- Если изменения версии не было — `build_number` инкрементится сам через git rev-list

### 3.3 Когда CI правится

Если в патче меняется структура проекта (новая подпапка с кодом, новая зависимость, новый ресурс) — Claude **сразу** проверяет, нужно ли править `.github/workflows/build.yml`. Самые частые случаи:
- Новая подпапка в `android/app/src/main/kotlin/...` — workflow должен копировать рекурсивно (`cp -r`, не `cp *.kt`)
- Новая подпапка в `lib/` — она уже копируется рекурсивно, но проверить
- Новые ассеты в `assets/` — нужно `pubspec.yaml` декларировать + workflow подхватит

## 4. Правила версионирования

### 4.1 Семвер обязателен

Везде — в коммитах, именах файлов, артефактах, beep — пишем **полную** `v<MAJOR>.<MINOR>.<PATCH>`:

- ✅ `v0.4.0`
- ❌ `v0.4`
- ❌ `v4`

### 4.2 Версия и build number

- `version: 0.4.0+1` в pubspec — версия пакета, `+1` это build number из pubspec (не используем для CI)
- В именах артефактов CI использует свой `<build_number>` = `git rev-list --count HEAD`
- Бамп версии в pubspec — когда есть значимое изменение функционала (новая версия recon, новые пробы). Patch-релизы (CI fixes, мелкие исправления) — не требуют бампа, build_number сам инкрементится.

### 4.3 Conventional commits

Сообщения коммитов:
- `v0.4.0: 7 read-only probes — ...` для версионных
- `CI: <что>` для правок workflow
- `fix: <что>` для багфиксов
- `docs: <что>` для документации

## 5. Правила безопасности (write-probes)

Этот раздел — НАПОМИНАНИЕ. Полный протокол — в файле `docs/WRITE_PROBE_PROTOCOL.md` (или `bz5_byd_binder_v0_1_0/WRITE_PROBE_PROTOCOL.md` если ещё не интегрирован).

### 5.1 Recon — read-only

`bz5-recon` любой версии **не делает write-операций ни в системе, ни в car framework**. Это правило не обсуждается. Если в patch предлагается метод, делающий `setProperty`, `setAcTempLevel`, `SystemProperties.set`, или похожее — это **ошибка Claude**, патч отвергается.

### 5.2 Write-probes — отдельные сессии, отдельные обсуждения

Любая write-операция:
1. Сначала обсуждается в чате (что пишем, зачем, чем это обратимо)
2. Кодом приходит **отдельным** патчем (не вперемешку с read-only)
3. В коде — обязательный pre-flight checklist и автоматический revert
4. Машина в `PARKED`, проверяется через `getDrivingState()`

## 7. Поддержание `docs/byd_internals_findings.md` актуальным

Файл `docs/byd_internals_findings.md` — это **живая** карта внутренностей машины. Не одноразовый артефакт, а растущий справочник, версионируемый в git.

### 7.1 Когда обновляем

Claude **сам** инициирует обновление findings, не дожидаясь явной просьбы пользователя, в следующих случаях:

- Прошёл успешный recon-запуск → JSON содержит новую информацию (новые сервисы, доступные permissions, accepted setting keys, transaction codes из forensic dump, и т. д.)
- Декомпилирован новый APK или классы из системы — появились новые AIDL сигнатуры, parcelable layouts, property names
- Подтверждена или опровергнута гипотеза о доступности какого-то API
- Найден новый системный property, intent, broadcast, ContentProvider
- Изменилось поведение после применения какой-то конфигурации (например, после toggle developer options)
- Получены новые сведения о SELinux-границах, signature-permissions, ro/sys/persist properties
- Эмпирически уточнены семантики числовых значений (например, что значит `drivingState=2`)

### 7.2 Как обновляем

- Новые факты добавляются в подходящий раздел (или создаётся новый, если темы нет)
- Старая, опровергнутая информация **не удаляется**, а помечается зачёркиванием и комментарием почему — это даёт историю гипотез
- Если факт основан на конкретном recon-запуске — указывается ссылка вроде `(verified: recon_v0.4.0_20260521_HHMMSS.json)`
- Если основан на декомпиляции — указывается источник (`com.byd.car.server v2.1.0-alpha10`)
- В самом верху файла ведётся короткий **Changelog** с датами и кратким описанием обновлений

### 7.3 Доставка

Обновления `byd_internals_findings.md` приходят как обычные патчи по схеме раздела 1, например:
- `bz5_recon_v0_4_0_patch_005_findings_recon_results.zip` (после запуска recon'а)
- `bz5_recon_v0_4_0_patch_007_findings_caller_parcelable.zip` (после декомпиляции `Caller`)

В архиве — только `docs/byd_internals_findings.md` (если ничего ещё не меняли) или комбо с другими файлами, если параллельно вносим code-правки на основании новых знаний.

### 7.4 Прочее

- Findings никогда не теряют закрытые/непубличные данные машины пользователя (VIN, ICCID, IMEI, точные координаты). Если они нужны для понимания, заменяются на `<redacted>`.
- Findings — это **наш** документ, не публичный. До MVP не уходит в открытые репозитории и не публикуется.
